# สเปกแอป Android POS (Native) — ระบบบริหารบัญชี ร้านค้าสหการ

> **สำหรับ Claude Code (เซสชันใหม่):** เอกสารนี้คือโจทย์ทั้งหมดสำหรับสร้างแอป Android แบบ Native
> ที่ทำงานแทนหน้า "ขายสินค้า (POS)" ของเว็บ และ **ขายต่อได้แม้ไม่มีอินเทอร์เน็ต**
> ฝั่งเซิร์ฟเวอร์ (PHP 8.1 + Slim 4 + MariaDB, repo `kinoppol/rvc.coac`) มี API ให้พร้อมแล้วตามหัวข้อ 5
> อย่าแก้ฝั่งเซิร์ฟเวอร์จากโปรเจกต์แอป ถ้า API ไม่พอให้จดไว้ในหัวข้อ "สิ่งที่ต้องขอเพิ่มจากเซิร์ฟเวอร์" ของ README แอป
>
> ข้อความทั้งหมดในแอปเป็น **ภาษาไทย** ผู้ใช้คือพนักงานขายหน้าร้านค้าสหการของวิทยาลัย (นักเรียน/ครู) ใช้บนแท็บเล็ตหรือมือถือ

---

## 1. เป้าหมาย

1. ทำได้ **ครบทุกฟังก์ชันของหน้า POS บนเว็บ** (หัวข้อ 3)
2. **โหลดข้อมูลสินค้าทั้งหมดครั้งแรก** (ชื่อ ราคา บาร์โค้ด แพ็ค สต๊อก ผู้ฝาก รูปภาพ) แล้ว **ครั้งต่อไปโหลดเฉพาะที่เปลี่ยน**
3. **บันทึกการขายลงเครื่องก่อนเสมอ** แล้วส่งขึ้นเซิร์ฟเวอร์เมื่อเชื่อมต่อได้ (ทันทีถ้าออนไลน์ หรือเบื้องหลังภายหลัง)
4. ส่งซ้ำได้โดยไม่บันทึกซ้ำ ไม่มีรายการขายสูญหาย แม้ปิดแอป แบตหมด หรือเน็ตหลุดกลางทาง
5. จับคู่เครื่องกับระบบด้วย **รหัสจับคู่ 6 ตัว** (แบบ Google TV) ไม่ต้องพิมพ์รหัสผ่านบนเครื่อง

## 2. เทคโนโลยีที่ต้องใช้

| ส่วน | ใช้ |
|---|---|
| ภาษา / UI | Kotlin, Jetpack Compose (Material 3), รองรับแนวนอน (แท็บเล็ต) และแนวตั้ง (มือถือ) |
| สถาปัตยกรรม | MVVM + Repository, Kotlin Coroutines/Flow, Hilt |
| ฐานข้อมูลในเครื่อง | Room (เปิด WAL) — แหล่งข้อมูลหลักของหน้าจอทั้งหมด (single source of truth) |
| เครือข่าย | Retrofit + OkHttp + kotlinx.serialization, timeout เชื่อมต่อ 5 วิ / อ่าน 20 วิ |
| งานเบื้องหลัง | WorkManager (ส่งยอดขาย, ซิงก์สินค้า, โหลดรูป) พร้อม constraint `NetworkType.CONNECTED` และ backoff แบบ exponential |
| ตรวจสถานะเครือข่าย | `ConnectivityManager.NetworkCallback` + ping `/ping` (มีเน็ตแต่เซิร์ฟเวอร์ล่ม ก็ถือว่าออฟไลน์) |
| รูปภาพ | Coil + เก็บไฟล์ใน `filesDir/product_images/{id}_{image_token}.jpg` (ไม่ใช้แค่ cache ชั่วคราว) |
| สแกนบาร์โค้ด | CameraX + ML Kit Barcode Scanning; และ **เครื่องสแกนแบบคีย์บอร์ด (USB/Bluetooth HID)** |
| เก็บความลับ | โทเคนเครื่องเก็บด้วย Android Keystore (EncryptedSharedPreferences หรือ DataStore + Tink) |
| ตั้งค่า | DataStore (ที่อยู่เซิร์ฟเวอร์, cursor ซิงก์, ค่าที่ผู้ใช้เลือก เช่น มุมมอง/การเรียง/ระดับเสียง) |
| minSdk / targetSdk | 26 / ล่าสุด |
| ทดสอบ | JUnit + Turbine + MockWebServer, Room in-memory, Compose UI test สำหรับเส้นทางขายหลัก |

## 3. ฟังก์ชันของหน้า POS ที่ต้องมี (เทียบกับเว็บ)

### 3.1 รายการสินค้า
- แสดงสินค้า **แบบรูปภาพ (grid)** หรือ **แบบรายการ (list)** — สลับได้ จำค่าที่เลือก
- **เรียง**: ขายดี (ค่าเริ่มต้น), ชื่อ ก-ฮ, ราคาต่ำ→สูง, ราคาสูง→ต่ำ, คงเหลือมาก→น้อย, คงเหลือน้อย→มาก
  - "ขายดี" ใช้จำนวนที่ขายใน 90 วัน จาก `GET /catalog/popular`
- **กลุ่ม**: ทั้งหมด / ไม่มีบาร์โค้ด / สินค้าฝากขาย (`consignor_id != null`)
- ค้นหาด้วยชื่อ (บางส่วนของคำ) หรือบาร์โค้ด ทั้งชื่อภาษาไทยและอังกฤษ ค้นในฐานข้อมูลเครื่อง (เร็ว ไม่รอเน็ต)
- ปกติแสดงเฉพาะสินค้าที่ `qty_stock > 0` เว้นแต่เปิด "ขายสินค้าคงเหลือต่ำกว่า 1" (ข้อ 3.4)
- ค้นแล้วเจอแต่สินค้าที่หมด: แสดงว่า "สินค้าหมด" ให้แคชเชียร์รู้ว่าทำไมขายไม่ได้
- แต่ละสินค้าแสดง: รูป (ถ้ามี) ชื่อ ราคา คงเหลือ ชื่อผู้ฝาก (หรือ "สินค้าของร้าน") และปุ่ม
  **"📦 ยกแพ็ค ×{pack_size} ฿{sale_price}"** สำหรับแพ็คที่ขายยกแพ็คได้ (พร้อมยอดที่ลดเทียบกับราคาชิ้น×จำนวน)

### 3.2 สแกนบาร์โค้ด
- **การกรองรายการขณะพิมพ์**: ตัวอักษรกรองตามปกติ ส่วนตัวเลขล้วนยังไม่กรองจนกว่าจะครบ 13 หลัก มีตัวอักษรปน หรือกดค้นหา
  (บาร์โค้ดระบุสินค้าหนึ่งตัวหรือไม่พบเลย จึงไม่ต้องกรองทุกปุ่ม) ทั้งเว็บและแอปหน่วง 120 มิลลิวินาทีเพื่อกรองครั้งเดียวเมื่อกดรัว
  กดค้นหาแล้วถ้าไม่มีรหัสตรงเป๊ะและพบหลายรายการ แสดงรายการให้เลือก (เช่น ค้น "500" ในชื่อสินค้า); รหัสที่ร้านสร้างเองสั้นกว่า 13 หลักยังเพิ่มลงตะกร้าได้ทันทีเมื่อเครื่องสแกนส่ง Enter
- **สแกนเจอสินค้า**: หยิบลงตะกร้าโดยไม่วาดรายการสินค้าใหม่ เว็บเปลี่ยนเฉพาะตัวเลขบนการ์ดของสินค้านั้น ระหว่างเครื่องสแกนส่งรหัสรายการจะไม่ถูกกรอง (วาดใหม่เมื่อรายการถูกกรองด้วยคำค้นอื่นอยู่เท่านั้น)
- **เครื่องสแกนคีย์บอร์ด**: ช่องค้นหารับปุ่มจากเครื่องสแกน (พิมพ์รัวแล้ว Enter) แตะหนึ่งครั้งเพิ่มลงตะกร้า
  - เครื่องสแกนที่ตั้งเป็นแป้นภาษาไทยจะได้ตัวอักษรไทย (เช่น "คคถต…") ต้องแปลงกลับเป็นตัวอักษรบนปุ่มเดียวกัน
    (ดู `KeyEvent.keyCode`/scan code แทนตัวอักษร) — เว็บทำแบบเดียวกัน
  - ปุ่มที่มาเร็วกว่า 35 มิลลิวินาทีต่อเนื่อง ≥3 ปุ่ม ถือว่าเป็นเครื่องสแกน: แสดงหน้าจอ "กำลังค้นหาสินค้า…" แล้วรอ Enter
- **กล้อง**: ปุ่มสแกนด้วยกล้อง สแกนต่อเนื่องได้หลายชิ้น มีเสียงและสั่นเมื่ออ่านได้ กันอ่านซ้ำบาร์โค้ดเดิมภายใน 1.2 วินาที
- ลำดับการหาจากบาร์โค้ด: `barcode` ของชิ้น → `packs[].barcode` (ขายยกแพ็คในราคาแพ็ค) → ถ้าเป็นข้อความ
  และเจอสินค้าเดียวให้เพิ่มเลย → ถ้าเป็นตัวเลข ≥4 หลักและไม่เจอในเครื่อง และออนไลน์ ให้ถาม `GET /sales/products?q=`
  (อาจเป็นสินค้าที่เพิ่งรับเข้า) แล้วบันทึกลงเครื่อง
- ไม่พบ: เสียงผิดพลาด + ข้อความ "ไม่พบสินค้าบาร์โค้ด {code} (หรือสินค้าหมด)"

### 3.3 ตะกร้า
- เพิ่มชิ้นละ 1 / เพิ่มยกแพ็ค / ปรับจำนวน (+ − และพิมพ์จำนวน) / ลบรายการ / ล้างตะกร้า (ยืนยันก่อน)
- **แพ็ค**: บรรทัดยกแพ็คเก็บ `pack_size`; จำนวนในตะกร้านับเป็น "แพ็ค" แต่ส่งไปเซิร์ฟเวอร์เป็น **จำนวนชิ้น**
  (`qty = แพ็ค × pack_size`) ราคา/ชิ้นของแพ็ค = `pack.sale_price / pack_size`
  - กดยกแพ็คของสินค้าที่มีบรรทัดชิ้นอยู่แล้ว: เอาชิ้นที่มีอยู่รวมเป็นแพ็ค (มี 1 ชิ้น กดแพ็ค ×12 = 1 แพ็ค ไม่ใช่ 1 ชิ้น + 1 แพ็ค)
    ชิ้นที่เกินหนึ่งแพ็คยังเป็นบรรทัดชิ้นต่อ — ตรวจสต๊อกโดยไม่นับชิ้นที่รวมเข้าแพ็คซ้ำ
- ตรวจสต๊อกตอนเพิ่ม: รวมทุกบรรทัดของสินค้าเดียวกัน (ชิ้น + แพ็ค×ขนาด) ต้องไม่เกิน `qty_stock`
  ถ้าเกินและไม่ได้เปิดขายเกินสต๊อก → ห้ามเพิ่ม + "{ชื่อ} มีคงเหลือเพียง {n} ชิ้น"
  ถ้าเปิดไว้ → เพิ่มได้ + เตือน "คงเหลือในระบบ {n} ชิ้น ขายได้ แต่สต๊อกจะติดลบ ควรตรวจนับ/บันทึกรับสินค้าภายหลัง"
- **พักตะกร้า** (⏸): เก็บตะกร้าปัจจุบันเป็นเลข #1, #2… พร้อมเวลา แล้วเริ่มตะกร้าใหม่; เปิดตะกร้าที่พักกลับมาได้
  (ถ้ามีตะกร้าปัจจุบันอยู่ ให้พักตะกร้านั้นแทนที่) — ตะกร้าและตะกร้าที่พักเก็บใน Room รอดการปิดแอป
- เมื่อข้อมูลสินค้าอัปเดต: ปรับราคาในตะกร้าตามราคาใหม่ เอาสินค้าที่หมดออก พร้อมแจ้ง "เอาออกจากตะกร้าเพราะสินค้าหมด: …"
- แสดงยอดรวมเงินและจำนวนชิ้น ปุ่ม **ชำระเงิน** ขนาดใหญ่

### 3.4 การตั้งค่าที่มาจากเซิร์ฟเวอร์ (`GET /me` → `pos`)
- `payment_methods`: วิธีชำระที่ร้านเปิด (`cash` เงินสด 💵, `transfer` โอนเงิน 🏦, `qr` สแกน QR 📱, `card` บัตร 💳)
- `payment_mixed`: บัญชีนี้ชำระแบบผสมได้ไหม
- `promptpay`: `null` = ไม่แสดง QR, หรือ `{target, title, account_name, merchant_code, warning_title, warning_detail}` — หน้าชำระเงินแสดงเต็มจอ มีคำเตือน (ว่าง = ไม่แสดง) และ Thai QR Payment เสมอ เหนือปุ่มวิธีชำระ ยอดใน QR คือยอดของแถว `qr` ถ้าไม่มีใช้ยอดที่วิธีอื่นที่ไม่ใช่เงินสดเหลือไว้ สร้างในเครื่อง (ออฟไลน์ได้) `target` เป็นเลขพร้อมเพย์ (10/13/15 หลัก) หรือข้อความจาก QR ร้านค้า (ขึ้นต้น `000201`, tag 29/30); ผู้ดูแลระบบตั้งที่เว็บ เปลี่ยนแล้ว `config_hash` เปลี่ยนด้วย
- `sell_out_of_stock`: บัญชีนี้มีสวิตช์ "เปิดขายสินค้าที่คงเหลือต่ำกว่า 1" ไหม (สวิตช์ของผู้ใช้ จำค่าในเครื่อง ต้องแสดงแถบเตือนตลอดเวลาที่เปิด "แตะเพื่อปิด")
- `sell_out_of_stock_always`: ทุกคนขายเกินสต๊อกได้เสมอ (ไม่มีสวิตช์)
- `store_hours`, `store_closed_days` (0=อาทิตย์…6=เสาร์), `store_holidays`: ใช้คำนวณ "วันบัญชี" (ข้อ 3.7)
- `sale_edit`: เปิดให้ขอแก้ไขการขายไหม และภายในกี่นาที

### 3.5 ชำระเงิน
- ยอดที่ต้องชำระ ปุ่มวิธีชำระ (เฉพาะที่ร้านเปิด) ค่าเริ่มต้นเป็นเงินสดเต็มจำนวน
- **ชำระแบบผสม** (ถ้า `payment_mixed`): สวิตช์ "ชำระแบบผสม" แล้วเลือกหลายวิธี ใส่จำนวนแต่ละวิธี ปุ่ม "ยอดที่เหลือ"
  - ถ้าแคชเชียร์ยังไม่ได้พิมพ์ยอดเงินสดเอง ยอดเงินสดตามยอดที่เหลือจากวิธีอื่นอัตโนมัติ
- เงินสด: ปุ่มเงินด่วน = ยอดพอดี + ปัดขึ้นเป็นทวีคูณของ 10, 20, 50, 100, 500, 1000 (ไม่ซ้ำ เรียงน้อยไปมาก สูงสุด 6 ปุ่ม)
- คำนวณ: `nonCash = ผลรวมวิธีที่ไม่ใช่เงินสด`, `cashDue = total − nonCash`, `เงินทอน = เงินสดที่รับ − cashDue`
  - ห้าม `nonCash > total` ("ยอดที่ไม่ใช่เงินสดเกินยอดที่ต้องชำระ"), ห้ามเงินสดน้อยกว่า `cashDue`
  - ปัดทศนิยม 2 ตำแหน่ง เปรียบเทียบด้วย tolerance 0.004 (เหมือนเซิร์ฟเวอร์)
- ยืนยัน → **บันทึกลง Room ก่อน** (สถานะ `PENDING`) แล้วค่อยส่ง (ข้อ 6.3)
- หน้าเสร็จสิ้น: "บันทึกการขายแล้ว" เลขที่เอกสาร (ถ้าส่งสำเร็จแล้ว) หรือ "บันทึกในเครื่องแล้ว · รอส่งเข้าระบบ"
  ยอดขาย **เงินทอนตัวใหญ่** ป้าย "ขายนอกเวลาทำการ · ลงบัญชีวันที่ …" ถ้า after_hours ปุ่ม "ขายรายการถัดไป"
- คีย์ลัดสำหรับคีย์บอร์ด: Enter = ยืนยัน/ถัดไป, Esc = ยกเลิก

### 3.6 เงินในลิ้นชัก (cash drawer)
- ก่อนขายวันแรกของวันบัญชี ต้อง **ระบุเงินในลิ้นชัก** (`POST /drawer/open {amount, note}`) หรือ
  **ข้ามชั่วคราว** (`POST /drawer/skip` ขายได้ `skip_seconds` วินาที นับเวลาจากนาฬิกาเครื่องเอง)
  - แถบเตือน "⏳ ยังไม่ได้ระบุเงินในลิ้นชัก ขายได้ชั่วคราวอีก m:ss นาที" พร้อมปุ่ม "ระบุเงินในลิ้นชัก"
  - ไม่ต้องระบุถ้า `drawer.required == false` (ขายนอกเวลาที่ลงบัญชีวันถัดไป)
- **ออฟไลน์**: นับเงินได้ บันทึกลงคิว (ส่ง `drawer/open` ก่อนยอดขายที่เกิดหลังจากนั้น) และขายต่อได้ทันที
  ถ้าส่งแล้วได้ "ระบุเงินในลิ้นชักของวันนี้ไปแล้ว" (เครื่อง/คนอื่นนับก่อน) ถือว่าสำเร็จ ทิ้งรายการนั้น
- ปิดยอด (`POST /drawer/close {amount, note}`) และดูสรุปลิ้นชัก (`GET /drawer/summary`) — ทำได้เฉพาะออนไลน์
  และควรทำหลังส่งยอดขายในคิวหมดแล้ว (บังคับ: ถ้ามีคิวค้าง ให้ส่งก่อน หรือแจ้งว่ายอดอาจไม่ครบ)

### 3.7 วันบัญชีและเวลาทำการ
คำนวณในเครื่องจาก `pos` (ต้องตรงกับเซิร์ฟเวอร์ `SettingsService::businessDay`):
```
businessDay(at):
  isClosed(d) = weekday(d) ∈ store_closed_days  OR  date(d) ∈ store_holidays
  nextOpen(d) = d+1 วันขึ้นไปจนกว่าจะไม่ใช่วันปิด (สูงสุด 60 วัน)
  day = วันที่ของ at
  if isClosed(day): return {date: nextOpen(day), after_hours: true, holiday: ชื่อวันหยุด(ถ้ามี)}
  if open == "" or close == "": return {date: day, after_hours: false}
  if HH:mm(at) >= close: return {date: nextOpen(day), after_hours: true}
  return {date: day, after_hours: HH:mm(at) < open}
```
- นอกเวลาทำการ: แถบ "🌙 นอกเวลาทำการ (เวลาทำการ 08:00–16:30 น.) รายการที่ขายตอนนี้จะลงบัญชีเป็นยอดขายวันที่ …"
  หรือ "วันนี้ร้านปิด ({ชื่อวันหยุด})"
- ใช้เขตเวลา `pos.timezone` (Asia/Bangkok) ไม่ใช่เขตเวลาของเครื่อง
- เซิร์ฟเวอร์คำนวณวันบัญชีจาก `sold_at` ที่ส่งไปเอง ค่าในเครื่องใช้เพื่อแสดงผลเท่านั้น

### 3.8 ประวัติการขายของฉัน และขอแก้ไขการขาย (ออนไลน์)
- รายการขายของเครื่องนี้ในเครื่อง (Room) แสดงได้เสมอ พร้อมสถานะ: รอส่ง / ส่งแล้ว (เลขที่) / บันทึกไม่สำเร็จ (ผู้ดูแลกำลังตรวจ)
- ประวัติจากเซิร์ฟเวอร์: `GET /sales/mine?from=YYYY-MM-DD&to=YYYY-MM-DD`, รายละเอียด `GET /sales/{id}`
- ขอแก้ไขการขาย (ภายใน `sale_edit.minutes` นาทีหลังขาย ต้องผ่านการอนุมัติของผู้จัดการ):
  `POST /sales/{id}/edit-requests {items:[{sale_item_id|product_id, qty, pack_size?}], payments:[{method, amount}], reason}`
  ยกเลิกคำขอ `POST /sale-edits/{id}/cancel`
  (รูปแบบเต็มดูจาก `src/Controllers/SaleEditController.php`, `src/Services/SaleEditService.php` และหน้าเว็บ `public/assets/js/views/mysales.js` ใน repo เซิร์ฟเวอร์)

### 3.9 อื่น ๆ ที่เว็บมี
- เสียง: สแกนสำเร็จ / ยกแพ็ค / เตือน / ผิดพลาด / ชำระเงินสำเร็จ — ปรับระดับเสียงได้ (ปิด/เบา/ปกติ/ดัง)
- โหมดเต็มหน้าจอ (immersive) และเปิดหน้าจอค้างไว้ระหว่างขาย (`FLAG_KEEP_SCREEN_ON`)
- ข้อความแจ้งเตือนสั้น ๆ ใต้แถบค้นหา (สำเร็จ/เตือน/ผิดพลาด)

## 4. หน้าจอของแอป

1. **ตั้งค่าเซิร์ฟเวอร์** (ครั้งแรก): ช่องที่อยู่ เช่น `https://coac.rvc.ac.th/web/public/`
   หรือปุ่ม **สแกน QR-Code** (หน้าเว็บ "อุปกรณ์ POS" แสดง QR ของที่อยู่นี้) → ตรวจด้วยการเรียก `POST /pair/start`
   - ยอมรับเฉพาะ `https://` (ยกเว้น build debug ที่อนุญาต http สำหรับทดสอบในวง LAN)
2. **จับคู่**: แสดงรหัสตัวใหญ่ `K7M-Q2X` (แบ่ง 3-3) + นับถอยหลัง 10 นาที + คำแนะนำ
   "ให้ผู้ดูแลระบบเปิดเมนู รายงานและระบบ › อุปกรณ์ POS (Android) แล้วกรอกรหัสนี้"
   และ QR-Code ของลิงก์ `{server}#/devices?code={CODE}` (ผู้ดูแลสแกนด้วยมือถือที่ล็อกอินอยู่ จะเปิดหน้าพร้อมรหัสให้)
   หมดเวลาแล้วขอรหัสใหม่อัตโนมัติ
3. **ซิงก์ครั้งแรก**: แถบความคืบหน้า "กำลังโหลดสินค้า 1,250 / ~3,000" และ "กำลังโหลดรูป 340 / 2,100"
   ขายได้ทันทีเมื่อโหลดข้อมูลสินค้าเสร็จ (รูปโหลดต่อเบื้องหลัง)
3.5 **เลือกโปรไฟล์ผู้ขาย** (ข้อ 5.8): การ์ดรูป/อักษรย่อของพนักงานขายแต่ละคนของเครื่อง แตะแล้วกรอก PIN (ถ้ามี)
   แสดงตอนเปิดแอป เมื่อกด "สลับผู้ขาย" และเมื่อไม่มีการใช้งานนานตามที่ตั้งไว้ (ค่าเริ่มต้นปิด)
4. **ขายสินค้า (POS)** — หน้าหลัก แท็บเล็ตแนวนอน: สินค้าซ้าย ตะกร้าขวา; มือถือ: สินค้าเต็มจอ + แถบตะกร้าด้านล่าง
   แถบสถานะบนสุด: 🟢 ออนไลน์ / 🔴 ออฟไลน์ · รอส่ง n รายการ · ซิงก์สินค้าล่าสุด hh:mm · **ชื่อผู้ขายที่ใช้งานอยู่ + ปุ่มสลับผู้ขาย**
5. **ชำระเงิน** (dialog/bottom sheet) และ **เสร็จสิ้น**
6. **เงินในลิ้นชัก** (นับเปิดร้าน / ข้าม / ปิดยอด / สรุป)
7. **ประวัติการขาย** (ในเครื่อง + จากเซิร์ฟเวอร์) และขอแก้ไขการขาย
8. **สถานะการซิงก์**: คิวรอส่ง รายการที่บันทึกไม่สำเร็จพร้อมเหตุผล ปุ่ม "ส่งตอนนี้" "โหลดสินค้าใหม่ทั้งหมด"
9. **ตั้งค่า**: ชื่อเครื่อง/รายชื่อผู้ขาย (อ่านอย่างเดียว) **ความถี่ในการส่งข้อมูลเบื้องหลัง** (ข้อ 5.9) เสียง มุมมอง ยกเลิกการจับคู่ในเครื่อง (ล้างข้อมูล — ห้ามถ้ายังมีคิวค้าง เว้นแต่ยืนยันสองชั้น)

## 5. API ของเซิร์ฟเวอร์

- Base URL: `{server}/api/device/v1` (เช่น `https://coac.rvc.ac.th/web/public/api/device/v1`)
- JSON UTF-8 ทุกคำขอ/คำตอบ ข้อผิดพลาด: `{"error": "ข้อความภาษาไทย", "code": "..."}` (code มีเฉพาะบางกรณี)
- ทุกคำขอหลังจับคู่ส่ง header:
  - `X-Device-Token: <token>` (หรือ `Authorization: Bearer <token>`)
  - `X-App-Version: 1.0.0`
  - `X-Pending-Sales: <จำนวนรายการขายที่ยังไม่ได้ส่ง>` (ผู้ดูแลเห็นในหน้าเว็บ)
  - `X-Device-User: <user id ของโปรไฟล์ที่ใช้งานอยู่>` (ข้อ 5.8) — คำขอออนไลน์ เช่น ลิ้นชัก ประวัติการขาย
    ทำในนามคนนี้; ไม่ส่ง = โปรไฟล์เริ่มต้นของเครื่อง
- ไม่มี cookie/session ไม่มี CSRF
- เวลาจากเซิร์ฟเวอร์: `YYYY-MM-DD HH:mm:ss` (เวลาไทย) หรือ ISO-8601 (`server_time`)

### สถานะ HTTP ที่ต้องจัดการ
| สถานะ | ความหมาย | แอปทำ |
|---|---|---|
| 401 `device_unpaired` / `device_revoked` | ไม่มี/ถูกยกเลิกโทเคน | หยุดส่ง **เก็บคิวไว้** แสดงหน้าจับคู่ใหม่ (หลังจับคู่ใหม่ เครื่องเป็นอุปกรณ์ใหม่ ส่งคิวเดิมต่อได้) |
| 403 `user_inactive` | บัญชีของโปรไฟล์นี้ถูกปิด | ออกจากโปรไฟล์นี้ กลับหน้าเลือกโปรไฟล์ (เรียก `/me` ใหม่) |
| 403 `user_not_on_device` | โปรไฟล์นี้ถูกนำออกจากเครื่องแล้ว | เหมือนข้างบน — คิวยอดขายเดิมของคนนี้ยังส่งได้ (ข้อ 5.8) |
| 403 (ไม่มี code) | ไม่มีสิทธิ์ | แสดงข้อความ |
| 503 `not_migrated` | เซิร์ฟเวอร์ยังไม่รัน migration | แสดงข้อความ ลองใหม่ภายหลัง |
| 5xx / timeout / ไม่มีเน็ต | เซิร์ฟเวอร์ล่ม | ถือว่าออฟไลน์ ลองใหม่ด้วย backoff |
| 422 | ข้อมูลไม่ถูกต้อง | แสดง `error` |

### 5.1 จับคู่ (ไม่ต้องมีโทเคน)
`POST /pair/start`
```json
{"device_name": "Galaxy Tab A9", "model": "SM-X110", "platform": "Android 14", "app_version": "1.0.0"}
```
→ 201
```json
{"pairing_id": 4, "pair_code": "MHDTTY", "pair_secret": "cff8…(64 hex)", "expires_at": "2026-11-03 21:36:20",
 "expires_in": 600, "poll_seconds": 3, "server_name": "ระบบบริหารบัญชี ร้านค้าสหการ", "api_version": 1}
```
429 = ขอบ่อยเกินไป (เกิน 10 รหัสที่ยังไม่หมดอายุต่อ IP)

`POST /pair/status` ทุก `poll_seconds` วินาที
```json
{"pairing_id": 4, "pair_secret": "cff8…"}
```
→ `{"status": "pending"}` | `{"status": "expired"}` | `{"status": "revoked"}` |
```json
{"status": "active", "token": "pd4_9f…(48 hex)",
 "device": {"id": 4, "name": "หน้าร้าน 1", "status": "active",
            "user": {"id": 2, "full_name": "สมชาย ใจดี", "username": "somchai", "role": "cashier"}, "paired_at": "…"}}
```
- เก็บ `token` ใน Keystore ทันที แล้วเรียก `GET /me` (การใช้โทเคนครั้งแรกทำให้ `pair_secret` ใช้ไม่ได้อีก)
- ถ้าคำตอบ `active` หายระหว่างทาง ให้ poll อีกครั้ง จะได้โทเคนใหม่ (อันเก่าใช้ไม่ได้)
- `device.user` = โปรไฟล์เริ่มต้น; รายชื่อผู้ขายทั้งหมดของเครื่องอยู่ใน `GET /me` → `users` (ผู้ดูแลเพิ่ม/เอาออกได้จากหน้าเว็บ)

- เรียกตอนเปิดแอป เมื่อกลับมาออนไลน์ และเมื่อ `config_hash` จาก `/ping` เปลี่ยน เก็บลง Room/DataStore เพื่อใช้ตอนออฟไลน์

ถ้า `config_hash` ต่างจากของ `/me` ล่าสุด ให้เรียก `/me` ใหม่ (ผู้ขาย/PIN เปลี่ยน)

`PUT /settings {"sync_level": "low", "changed_at": "2026-11-03T22:50:00+07:00"}` → `{"sync": {…}}`
ผู้ใช้เปลี่ยนความถี่ในแอป (ข้อ 5.9) — ถ้าเปลี่ยนตอนออฟไลน์ให้ส่งเมื่อออนไลน์พร้อม `changed_at` = เวลาที่เปลี่ยน;
ค่าที่ตั้งทีหลังชนะ (ถ้าผู้ดูแลเปลี่ยนในเว็บทีหลัง เซิร์ฟเวอร์ไม่เปลี่ยนตาม และตอบค่าปัจจุบันกลับมา — ใช้ค่าที่ตอบเสมอ)

### 5.3 สินค้า (ซิงก์)
`GET /catalog?since=<cursor>&limit=500&discontinued=1` (limit สูงสุด 2000)

`discontinued=1`: ส่งสินค้าที่เลิกจำหน่ายมาด้วย พร้อม `"discontinued": true` — แอปไม่แสดงในรายการและการค้นชื่อ แต่สแกนบาร์โค้ดที่ตรงยังหยิบลงตะกร้าได้แม้ออฟไลน์ (ขายแม้คงเหลือ 0) ถ้าไม่ส่งพารามิเตอร์นี้ (แอปรุ่นเก่า) สินค้าเลิกจำหน่ายจะไม่อยู่ใน catalog และ `ids`
```json
{"products": [
   {"id": 1, "name": "ขนมทดสอบ", "barcode": "8850001", "sale_price": 10, "qty_stock": 5,
    "consignor_id": 1, "consignor_name": "ผู้ฝากทดสอบ", "image_token": "a1b2…", "image_url": "products/1/photo?size=thumb&v=a1b2…",
    "has_thumb": true, "packs": [{"barcode": "18850001", "pack_size": 12, "sale_price": 110}],
    "updated_at": "2026-11-03 21:24:11"}],
 "has_more": true, "next": "MjAyNi0xMS0wMyAyMToyNDoxMXwx", "server_time": "…",
 "ids": [1, 2, 3]}
```
- ส่งสินค้าทุกรายการ **รวมที่หมดแล้ว** เรียงตามเวลาที่เปลี่ยน; `packs` = เฉพาะแพ็คที่ขายยกแพ็คได้ (มีราคา) ส่งมาทั้งชุดทุกครั้ง
- `consignor_id = null` = สินค้าของร้าน
- อัลกอริทึม:
  1. ครั้งแรก (หรือ "โหลดใหม่ทั้งหมด"): ไม่ส่ง `since` วนเรียกโดยส่ง `since = next` จนกว่า `has_more = false`
  2. เก็บ `next` ของหน้าสุดท้ายไว้ (DataStore `catalog_cursor`) — ครั้งต่อไปเริ่มจาก cursor นี้ จะได้เฉพาะที่เปลี่ยน
  3. upsert ทุกสินค้าที่ได้ (ได้ซ้ำได้ ไม่เป็นไร) — **ทำในทรานแซกชันเดียวต่อหน้า**
  4. หน้าสุดท้ายของคำขอที่มี `since` มี `ids` = id สินค้าทั้งหมดที่ยังอยู่ → ลบสินค้าในเครื่องที่ไม่อยู่ในรายการ
     (สินค้าถูกรวม/ลบ) แต่ **อย่าลบสินค้าที่อยู่ในตะกร้า/คิวรอส่ง** ให้ซ่อนแทน
  5. ครั้งแรกแบบเต็ม: แทนที่ทั้งตารางหลังโหลดครบ (ไม่ลบก่อนโหลดเสร็จ ถ้าล้มกลางทางยังขายด้วยข้อมูลเดิมได้)
- **สต๊อกในเครื่อง**: `qty_stock` จากเซิร์ฟเวอร์ ลบด้วยจำนวนในรายการขายของเครื่องที่ยังไม่ส่ง (เมื่อส่งสำเร็จ เซิร์ฟเวอร์หักให้แล้ว)
  เก็บ `server_qty_stock` แยก แล้วคำนวณ `available = server_qty_stock − pending_qty`
- รอบซิงก์: ทุก `sync.catalog_seconds` ขณะออนไลน์และแอปเปิดอยู่ (ข้อ 5.9) + ดึงลงเพื่อรีเฟรช; WorkManager periodic 15 นาทีเมื่ออยู่เบื้องหลัง
  (ระดับ `minimal` ใช้รอบของระดับนั้นแม้อยู่เบื้องหลัง)
  "โหลดใหม่ทั้งหมด" อัตโนมัติวันละครั้งตอนเช้า (ครั้งแรกที่ออนไลน์ของวัน) เพื่อแก้ข้อมูลเพี้ยน เช่น ชื่อผู้ฝากเปลี่ยน

`GET /catalog/popular` → `{"data": [[product_id, ขายได้ใน 90 วัน], …]}` วันละครั้ง สำหรับเรียง "ขายดี"

**รูปภาพ**: `GET {server}/api/device/v1/{image_url}` (ต้องส่ง `X-Device-Token`) ได้ JPEG ขนาดย่อ
- โหลดเมื่อ `image_token` เปลี่ยน (ไฟล์ชื่อมี token จึงไม่ต้องตรวจซ้ำ) ลบไฟล์ของ token เก่า
- โหลดเบื้องหลังทีละ 4 ไฟล์ เฉพาะ Wi-Fi โดยค่าเริ่มต้น (ตั้งค่าให้ใช้เน็ตมือถือได้) 404 = ไม่มีรูป ข้ามไป
- `image_token = null` = ไม่มีรูป แสดงตัวอักษรแรกของชื่อแทน

`GET /sales/products?q=<บาร์โค้ดหรือชื่อ>` (ออนไลน์เท่านั้น — ค้นสินค้าที่ยังไม่อยู่ในเครื่อง ผลลัพธ์รูปแบบเดียวกับเว็บ:
`{"data": [{"id","name","barcode","sale_price","qty_stock","image_token","consignor_id","consignor_name","sold_qty","has_thumb","packs"}]}`)

### 5.4 ส่งยอดขาย
`POST /sales` — ส่งได้ครั้งละไม่เกิน 50 รายการ **เรียงตามเวลาขาย** (ส่งเกิน: เซิร์ฟเวอร์บันทึก 50 รายการแรก
คืน `results` เฉพาะรายการเหล่านั้น และ `remaining` = จำนวนที่ยังไม่ได้ทำ ให้ส่งต่อรอบถัดไปทันที)
· รายการไหนเซิร์ฟเวอร์บันทึกไม่ได้จะได้ผลของรายการนั้นเอง ไม่ทำให้ทั้งชุดล้ม (ออฟไลน์ → `failed`, ออนไลน์ → `rejected`)
· `rejected` "กำลังบันทึกรายการนี้อยู่ ส่งใหม่อีกครั้ง" = ชนกับเครื่องอื่นชั่วคราว ส่งใหม่ (UUID เดิม) ได้แม้เป็นรายการออฟไลน์
```json
{"sales": [{
  "client_uuid": "0f8c6a3e-2b1d-4c55-9a7e-1d2c3b4a5f60",
  "user_id": 5,
  "sold_at": "2026-11-03T10:15:42+07:00",
  "offline": true,
  "allow_short": false,
  "items": [
    {"product_id": 1, "qty": 2, "unit_price": 10},
    {"product_id": 7, "qty": 24, "pack_size": 12}
  ],
  "payments": [{"method": "cash", "amount": 100}, {"method": "transfer", "amount": 50}],
  "total_value": 245
}]}
```
- `client_uuid`: UUID v4 สร้างตอนกดยืนยันชำระ **ครั้งเดียว** ใช้ตลอดอายุรายการนั้น (ห้ามสร้างใหม่ตอนส่งซ้ำ)
- `user_id`: **ผู้ขายที่ขายรายการนี้** (โปรไฟล์ที่ใช้งานอยู่ตอนกดยืนยันชำระ) — เก็บไว้กับรายการ ห้ามใช้โปรไฟล์ปัจจุบันตอนส่ง
  ส่งรายการของหลายคนในชุดเดียวกันได้; ไม่ส่ง = ผู้ใน `X-Device-User`
- `sold_at`: เวลาที่กดยืนยันชำระ ISO-8601 พร้อม offset
- `offline`: `true` ถ้าตอนกดยืนยันส่งไม่สำเร็จทันที/ไม่ได้ออนไลน์ (รายการที่ลูกค้าจ่ายและไปแล้ว) — `false` เฉพาะการส่งทันทีขณะลูกค้ายังอยู่
- `items[].qty` เป็น **จำนวนชิ้น** เสมอ (แพ็ค: ทวีคูณของ `pack_size`), `unit_price` = ราคา/ชิ้นที่เครื่องคิด (บรรทัดแพ็คไม่ต้องส่ง)
- `payments[].amount` ของเงินสด = เงินที่รับมา (รวมเงินทอน) เหมือนเว็บ
- `allow_short`: สวิตช์ขายเกินสต๊อกเปิดอยู่ไหม

→ 200
```json
{"results": [
  {"client_uuid": "0f8c…", "status": "synced", "warnings": ["ขนมทดสอบ ขายราคา ฿9.00 (ราคาปัจจุบัน ฿10.00)"],
   "sale": {"id": 3, "doc_no": "SL-691103-002", "total_qty": 26, "total_value": 245, "change": 0,
            "business_date": "2026-11-03", "after_hours": false}}
 ], "server_time": "…"}
```
| `status` | ความหมาย | แอปทำ |
|---|---|---|
| `synced` | บันทึกแล้ว | เก็บ `doc_no`, `sale.id` → SYNCED, แสดง `warnings` ในประวัติ |
| `duplicate` | เคยบันทึกแล้ว (ส่งซ้ำ) | ทำเหมือน `synced` (ถ้ามี `error` "ผู้ดูแลระบบจัดการรายการนี้แล้ว" → RESOLVED) |
| `failed` | เป็นรายการออฟไลน์ที่บันทึกไม่ได้ (เช่น สินค้าถูกลบ) เซิร์ฟเวอร์ **เก็บไว้ให้ผู้ดูแลแก้แล้ว** | ทำเป็น FAILED_ON_SERVER ไม่ต้องส่งอีก แสดงเหตุผล |
| `rejected` | ออนไลน์ (`offline:false`) แต่ข้อมูลไม่ผ่าน เช่น สต๊อกไม่พอ วิธีชำระไม่เปิด | แสดง `error` ในหน้าชำระเงินให้แคชเชียร์แก้ แล้วส่งใหม่ด้วย **UUID เดิม** ได้; ถ้าลูกค้าไปแล้ว ให้ส่งใหม่เป็น `offline:true` |
| `drawer_required` | ออนไลน์และยังไม่ได้ระบุเงินในลิ้นชัก | เปิดหน้าระบุเงินในลิ้นชัก แล้วส่งใหม่ (UUID เดิม) |

เซิร์ฟเวอร์ทำกับรายการ `offline: true`: บันทึกตามที่ขายจริง ยอมให้สต๊อกติดลบ ใช้ราคาที่เครื่องส่ง
ยอมรับวิธีชำระที่ปิดไปแล้ว ลงวันบัญชีตาม `sold_at` (ถ้า `sold_at` ล้ำหน้าเวลาเซิร์ฟเวอร์เกิน 10 นาที ใช้เวลาที่ได้รับแทน)
และแจ้ง `warnings` เป็นภาษาไทย — รวมถึงผู้ขายที่ถูกนำออกจากเครื่องไปแล้ว (ยังบันทึกเป็นของคนนั้น พร้อมคำเตือน);
ผู้ขายที่ไม่เคยอยู่ในเครื่องหรือบัญชีถูกปิด → `failed` (ออนไลน์ → `rejected`)

### 5.7 แจกจ่ายและอัปเดตแอป (ไม่ต้องมีโทเคน)
ผู้ดูแลอัปโหลดไฟล์ .apk ที่หน้า "อุปกรณ์ POS (Android)" ของเว็บ พนักงานดาวน์โหลดจากปุ่มหรือ QR-Code ในหน้านั้น
(ที่อยู่อยู่นอก `/api/device/v1`):

| คำขอ | ใช้ |
|---|---|
| `GET {server}api/app/pos.json` | `{"data": {"version": "1.2.3", "version_code": null, "size": 2600235, "sha256": "…", "note": "…", "uploaded_at": "…", "uploaded_by": "…", "url": "api/app/pos.apk"}}` — `data` เป็น `null` ถ้ายังไม่มีไฟล์ |
| `GET {server}api/app/pos.apk` | ไฟล์ติดตั้งล่าสุด (`application/vnd.android.package-archive`) — 404 ถ้ายังไม่มี |

แอปควรเช็ค `pos.json` ตอนเปิดแอป/ทุกวันเมื่อออนไลน์ ถ้า `version` ใหม่กว่า `BuildConfig.VERSION_NAME`
(เทียบแบบ semver) ให้แสดงแถบ "มีแอปเวอร์ชันใหม่" → ดาวน์โหลดด้วย `DownloadManager` ตรวจ SHA-256 ให้ตรง
แล้วเปิดตัวติดตั้งผ่าน `FileProvider` + `ACTION_VIEW` (ต้องขอ `REQUEST_INSTALL_PACKAGES`)
— ห้ามอัปเดตระหว่างมีตะกร้าค้างหรือยอดขายยังส่งไม่หมดโดยไม่เตือน · ต้องเซ็นทุกเวอร์ชันด้วยคีย์เดียวกัน
และเพิ่ม `versionCode` ทุกครั้ง ไม่เช่นนั้นติดตั้งทับไม่ได้ (ข้อมูลในเครื่องจะหายถ้าต้องถอนแอปก่อน)

### 5.8 ผู้ขายหลายคนต่อเครื่องและการสลับโปรไฟล์
ผู้ดูแลเลือกพนักงานขายของเครื่องได้หลายคน (หน้าเว็บ "อุปกรณ์ POS") และตั้ง PIN ตัวเลข 4–6 หลักให้แต่ละคนได้
- แอปเก็บ `me.users` ทั้งหมดไว้ในเครื่อง เพื่อ**สลับโปรไฟล์ได้แม้ออฟไลน์**
- PIN ตรวจในเครื่อง: `sha256(salt + pin)` เป็น hex ตัวเล็ก ต้องเท่ากับ `pin.hash` (`pin = null` = ไม่ต้องกรอก)
  กรอกผิด 5 ครั้ง → ล็อก 1 นาที; ห้ามเก็บ PIN ที่กรอกไว้
- สลับโปรไฟล์: ตะกร้า/ตะกร้าที่พักแยกตามโปรไฟล์ (หรือถามว่าจะโอนตะกร้าให้คนใหม่ไหม) · ส่งคิวยอดขายทันทีถ้าออนไลน์ ·
  คำขอออนไลน์หลังจากนี้ใส่ `X-Device-User` ของคนใหม่ · ลิ้นชักเงินเป็นของแต่ละคน (`users[].drawer`) ต้องนับเงินเปิดของตนก่อนขาย
- เก็บ `user_id` ในทุก `local_sale` และ `drawer_action` (ส่ง `drawer_action` ด้วย `X-Device-User` ของเจ้าของรายการ)
- โปรไฟล์หายจาก `me.users` (ถูกนำออก/บัญชีปิด): ออกจากโปรไฟล์นั้น แต่**ยังส่งคิวยอดขายเดิมของคนนั้นต่อ**
- ประวัติการขาย (`/sales/mine`) แสดงของโปรไฟล์ที่ใช้งานอยู่

### 5.9 ความถี่ในการส่งข้อมูลเบื้องหลัง
แม้เน็ตใช้ได้ปกติ ร้านอาจลดการส่งข้อมูลเพื่อให้เครื่องทำงานลื่น — ตั้งได้ทั้งในหน้าเว็บ (ต่อเครื่อง) และในแอป (หน้าตั้งค่า)
**ค่าเริ่มต้น `medium` (ปานกลาง)** ค่าที่ใช้มาจาก `sync` (อย่าฝังตัวเลขในแอป ให้ใช้วินาทีที่เซิร์ฟเวอร์ส่ง):

| level | ชื่อ | ส่งยอดขาย (`sales_seconds`) | อัปเดตสินค้า (`catalog_seconds`) | ตรวจเซิร์ฟเวอร์ (`ping_seconds`) |
|---|---|---|---|---|
| `realtime` | ทันที | ทันทีที่ขาย | 1 นาที | 30 วินาที |
| `high` | ถี่ | 30 วินาที | 3 นาที | 1 นาที |
| `medium` | ปานกลาง | 2 นาที | 10 นาที | 2 นาที |
| `low` | น้อย | 10 นาที | 30 นาที | 5 นาที |
| `minimal` | ประหยัดที่สุด | 30 นาที | 2 ชั่วโมง | 15 นาที |

- `sales_seconds`: ระยะที่รายการที่ขายเสร็จรอได้ก่อนส่ง (รวบส่งเป็นชุด) — นับจากรายการเก่าสุดที่รอส่ง
- ไม่ว่าระดับใด **ส่งทันที** เมื่อ: รายการรอส่งถึง `flush_pending` (20), ปิดยอดลิ้นชัก, สลับโปรไฟล์, กด "ส่งตอนนี้",
  ก่อนอัปเดตแอป/ยกเลิกการจับคู่ในเครื่อง
- ระดับนี้ไม่เกี่ยวกับการส่งทันทีตอนกดชำระ (ข้อ 6.3 ข้อ 2) ซึ่งทำเฉพาะระดับ `realtime`;
  ระดับอื่นบันทึกลงเครื่องแล้วให้คิวส่งตามรอบ (ส่ง `offline=true` เพราะลูกค้าไปแล้ว) — ลิ้นชักที่ยังไม่นับเงินตรวจจาก `users[].drawer` ในเครื่อง
- หน้าเว็บแสดงเครื่องว่า "ออนไลน์" ถ้าเห็นภายใน 2.5 เท่าของ `ping_seconds` (อย่างน้อย 5 นาที)
- หน้าตั้งค่าในแอป: รายการ `sync_levels` แสดง `label` + `description` และบอกว่าตั้งล่าสุดจากไหน (`changed_by`: web/app)

### 5.10 รับฝากสินค้าและตรวจนับสต๊อก (ออนไลน์)
ใช้ API เดียวกับหน้าเว็บผ่านโทเคนเครื่อง สิทธิ์ตามบัญชีของผู้ใช้งานอยู่ (`X-Device-User`) — แอปแสดงเมนูเฉพาะผู้มีสิทธิ์
- **รับฝากสินค้า** (`receive.create`; ย้อนหลัง `receive.backdate`): `GET /consignors/options`, `POST /receive/quote`,
  `GET /receive/history?consignor_id=&q=`, `POST /receive/existing`, `POST /receive`, `GET /receive/requests`,
  `POST /receive/requests/{id}/reject`, `GET /receive/docs?q=`, `GET /receive/docs/{id}`, `POST /receive/docs/{id}/cancel` (ผู้ดูแลระบบ)
- **ตรวจนับสต๊อก** (`stockcount.create`; ส่งรายงาน `stockcount.submit`; อนุมัติ/ส่งกลับ `stockcount.approve`):
  `GET /stockcounts`, `GET /stockcounts/{id}`, `POST /stockcounts/start`, `GET /stockcounts/{id}/lookup?code=`,
  `GET /stockcounts/{id}/search?q=`, `POST /stockcounts/{id}/count` (ต้องมีรูป `photo`), `POST /stockcounts/{id}/barcode`,
  `POST /stockcounts/{id}/submit|approve|reopen|cancel`, `POST /products/{id}/photo`
- **นับสต๊อกทันที** (ไม่มีรอบเปิด, `stockcount.approve`): `GET /inventory/lookup`, `GET /inventory/search`,
  `POST /products/{id}/quick-count`, `POST /inventory/{id}/assign-barcode` (`purchase.create`)
- บาร์โค้ดที่ร้าน/ผู้ฝากสร้างเอง (ไม่ใช่ EAN-13) ใช้ได้ตามปกติ: แอปค้นหาก่อนเสมอ เตือนเฉพาะรหัสที่ไม่พบและดูเหมือน EAN-13 ที่อ่านผิด

## 6. ข้อมูลในเครื่องและการซิงก์

### 6.1 ตาราง Room (ขั้นต่ำ)
```
product(id PK, name, barcode, sale_price, server_qty_stock, consignor_id, consignor_name,
        image_token, image_path, sold_qty_90d, updated_at, hidden)
product_pack(product_id, barcode, pack_size, sale_price)          -- PK(product_id, pack_size, barcode)
cart_line(id PK, cart_id, product_id, qty, pack_size, unit_price, name_snapshot)
held_cart(id PK, no, held_at)                                      -- cart_id 0 = ตะกร้าปัจจุบัน
local_sale(client_uuid PK, user_id, sold_at, business_date, after_hours, total_value, total_qty, change,
           offline, allow_short, payload_json, status, doc_no, server_sale_id, error, warnings_json,
           attempts, last_attempt_at, created_at)
local_sale_line(client_uuid, product_id, name, qty, pack_size, unit_price)   -- สำหรับแสดงและคำนวณ pending_qty
drawer_action(id PK, user_id, kind[open|close|skip], amount, note, created_at, status, error)
seller_profile(id PK, username, full_name, role, permissions_json, pos_json, drawer_json, is_default, pin_salt, pin_hash)
kv(key PK, value)                                                  -- หรือใช้ DataStore (โปรไฟล์ที่ใช้งานอยู่, sync, config_hash)
```
สถานะ `local_sale.status`: `PENDING` → `SENDING` → `SYNCED` | `FAILED_ON_SERVER` | `RESOLVED` | `NEEDS_FIX`(rejected ออนไลน์)
FTS4 บน `product.name` + index บน `barcode`, `product_pack.barcode` เพื่อค้นหาเร็ว

### 6.2 กติกาสำคัญ
- **บันทึกลง Room ในทรานแซกชันเดียวกับการล้างตะกร้า** ก่อนแสดงหน้า "บันทึกแล้ว" — ถ้าแอปตายหลังจากนี้ ยอดไม่หาย
- `payload_json` เก็บสิ่งที่จะส่ง **ตายตัว** ตั้งแต่ตอนขาย (ราคา/รายการไม่เปลี่ยนตามการซิงก์สินค้าภายหลัง)
- ห้ามลบ `local_sale` ที่ยังไม่ SYNCED/RESOLVED ไม่ว่ากรณีใด ลบรายการ SYNCED ที่เก่ากว่า 30 วันได้
- รายการ SENDING ค้างตอนเปิดแอป (แอปตายระหว่างส่ง) → กลับเป็น PENDING แล้วส่งใหม่ (UUID เดิม เซิร์ฟเวอร์ตอบ duplicate)

### 6.3 การส่งยอดขาย
1. กดยืนยันชำระ → บันทึก `PENDING` (`offline=false` ถ้าตอนนี้ออนไลน์)
2. ถ้าออนไลน์ **และระดับความถี่เป็น `realtime`**: ส่งทันทีรายการเดียว รอไม่เกิน 8 วินาที (ระดับอื่นข้ามไปข้อ 3 ด้วย `offline=true`)
   - `synced` → แสดงเลขที่เอกสาร
   - `rejected`/`drawer_required` → กลับไปหน้าชำระเงินพร้อมข้อความ (ตะกร้าคืนมา) — แคชเชียร์แก้แล้วยืนยันใหม่ (UUID เดิม)
     หรือกด "ลูกค้าจ่ายแล้ว บันทึกไว้ส่งภายหลัง" → `offline=true`
   - timeout/เน็ตหลุด → ตั้ง `offline=true` แสดง "บันทึกในเครื่องแล้ว · รอส่งเข้าระบบ" (ขายต่อได้ทันที)
3. คิวเบื้องหลัง (WorkManager unique work `sales-sync`, `ExistingWorkPolicy.KEEP`):
   ส่ง `drawer_action` ที่ค้างก่อน แล้วส่ง `local_sale` สถานะ PENDING เรียงตาม `sold_at` ทีละ 50 จนหมด
   ล้มเหลวทางเครือข่าย → `Result.retry()` (backoff 30 วิ → สูงสุด ~1 ชม.)
4. เรียกคิวเมื่อ: ครบ `sync.sales_seconds` นับจากรายการเก่าสุดที่รอ, รอส่งถึง `flush_pending`, เน็ตกลับมา (NetworkCallback),
   เปิดแอป, ปิดยอดลิ้นชัก, สลับโปรไฟล์, ทุก 15 นาที (periodic เมื่ออยู่เบื้องหลัง), กด "ส่งตอนนี้"
5. แจ้งเตือน (notification) ถ้ามีรายการค้างเกิน 24 ชั่วโมง หรือมี FAILED_ON_SERVER

### 6.4 ความขัดแย้งของข้อมูล
- ราคาเปลี่ยนระหว่างออฟไลน์: เครื่องขายราคาเดิม เซิร์ฟเวอร์ยอมรับและเตือน (ผู้ดูแลเห็น)
- สต๊อกขายเกินเพราะหลายเครื่องขายพร้อมกัน: เซิร์ฟเวอร์ยอมรับรายการออฟไลน์และเตือนสต๊อกติดลบ
- สินค้าถูกลบ/รวม: เซิร์ฟเวอร์ตอบ `failed` เก็บไว้ให้ผู้ดูแลจัดการในหน้า "อุปกรณ์ POS" (บันทึกอีกครั้ง/จัดการแล้ว)
- ผู้ดูแลนำผู้ขายออกจากเครื่อง: รายการที่คนนั้นขายไว้ตอนออฟไลน์ยังบันทึกเป็นของคนนั้น (พร้อมคำเตือน) เพราะทุกรายการมี `user_id`

## 7. ความปลอดภัย
- โทเคนเก็บใน Keystore ห้ามเขียนลง log; ปิด `android:allowBackup` หรือยกเว้นไฟล์โทเคน
- บังคับ HTTPS ใน release (`network_security_config` ห้าม cleartext)
- ไม่เก็บรหัสผ่านของผู้ใช้ใด ๆ ในแอป (ใช้การจับคู่เท่านั้น) · PIN สลับโปรไฟล์เก็บเฉพาะ salt/hash ที่เซิร์ฟเวอร์ส่งมา
- หน้าตั้งค่า/ยกเลิกการจับคู่ในเครื่องควรล็อกด้วย PIN ของร้าน (ตั้งในเครื่อง) เพื่อกันนักเรียนกดเล่น
- ถ้าได้ 401 `device_revoked` ห้ามลบคิวยอดขายในเครื่อง

## 9. เกณฑ์การตรวจรับ (ต้องทดสอบได้ทั้งหมด)
1. จับคู่: แอปแสดงรหัส → กรอกในเว็บ → แอปเข้าหน้าโหลดสินค้าภายใน 5 วินาที; รหัสหมดอายุ 10 นาทีแล้วขอใหม่เอง
2. โหลดสินค้า 5,000 รายการครั้งแรกได้โดยไม่ค้าง (เป็นหน้า ๆ) ครั้งต่อไปแก้ราคา 1 รายการในเว็บ → แอปได้รายการเดียว
3. รูปสินค้าแสดงได้ตอนปิดเน็ต (โหลดไว้แล้ว)
4. **ปิด Wi-Fi/เน็ต** แล้วขาย 20 รายการ (เงินสด โอน ผสม ยกแพ็ค) → ทุกรายการแสดง "รอส่ง" สต๊อกในเครื่องลดลง
5. ปิดแอป (force stop) แล้วเปิดใหม่ → รายการรอส่งยังอยู่ครบ ตะกร้าที่พักยังอยู่
6. เปิดเน็ต → ทั้ง 20 รายการส่งเองภายใน 1 นาที ได้เลขที่เอกสาร ไม่มีรายการซ้ำในรายงานของเว็บ
7. จำลองเน็ตหลุดหลังเซิร์ฟเวอร์บันทึก (ตัดการเชื่อมต่อก่อนได้คำตอบ) → ส่งซ้ำแล้วได้ `duplicate` ยอดไม่ซ้ำ
8. ขายออฟไลน์เกินสต๊อก → เซิร์ฟเวอร์บันทึกพร้อมคำเตือน แอปแสดงคำเตือนในประวัติ
9. ลบสินค้าในเว็บ แล้วส่งรายการออฟไลน์ของสินค้านั้น → `failed` แสดงในหน้าเว็บ "อุปกรณ์ POS" และในแอป
10. ยกเลิกการจับคู่ในเว็บ → แอปแจ้งภายในรอบถัดไป ไม่ลบคิว จับคู่ใหม่แล้วคิวส่งต่อได้
11. ขายนอกเวลาทำการ/วันหยุด → แถบแจ้งและ `business_date` ตรงกับที่เซิร์ฟเวอร์คำนวณ
12. เครื่องสแกนบาร์โค้ดแบบคีย์บอร์ดที่ตั้งเป็นแป้นภาษาไทยสแกนได้ถูกต้อง
13. ผู้ขาย 2 คนในเครื่องเดียว: ปิดเน็ต ขายสลับกันคนละ 3 รายการ (กรอก PIN) → เปิดเน็ต ยอดเข้าเว็บเป็นของแต่ละคนถูกต้อง
    ลิ้นชักแยกกัน; ผู้ดูแลเอาคนหนึ่งออก → แอปเอาโปรไฟล์ออก แต่รายการค้างของคนนั้นยังส่งได้
14. เปลี่ยนความถี่ในเว็บเป็น "น้อย" → แอปเปลี่ยนรอบภายในรอบ ping ถัดไป; เปลี่ยนในแอปเป็น "ถี่" → หน้าเว็บแสดง "ถี่ (ตั้งจากแอป)";
    ระดับ "ปานกลาง": ขาย 1 รายการ ยอดเข้าระบบภายใน ~2 นาที; ขาย 20 รายการติดกัน ส่งทันที
15. Unit test: PaymentCalculator (รวมเงินทอนและปุ่มเงินด่วน), BusinessDay (วันหยุดยาว/หลังปิดร้าน), การรวมชิ้นเป็นแพ็ค, การคำนวณสต๊อกคงเหลือ

## 11. ทดสอบกับเซิร์ฟเวอร์
- ใช้เซิร์ฟเวอร์ทดสอบ/สำเนา ไม่ใช่ระบบจริงของร้าน (ยอดขายที่ส่งเข้าไปคือยอดขายจริงในบัญชี)
- ผู้ดูแลระบบหรือผู้จัดการร้านเท่านั้นที่จับคู่ได้ (สิทธิ์ `devices.manage`)
- ตรวจผลในเว็บ: เมนู **อุปกรณ์ POS (Android)** (สถานะเครื่อง จำนวนรอส่ง รายการไม่สำเร็จ),
  **ประวัติการขายของฉัน** ของบัญชีผู้ขาย และ **รายงานสรุป**
